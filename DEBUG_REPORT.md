# Отчёт аудита и отладки VK Video Desktop

Дата проверки: 12.09.2026

Проверен текущий рабочий каталог Z:\Windows\VK_Video_Desktop. В область аудита вошли исходники C#, XAML, проекты .NET, настройки сборки, CI, установщик, деинсталлятор и тесты. Каталоги bin и obj рассматривались как генерируемые результаты и не анализировались как исходный код. Инструкции из AGENTS.md использованы как правила проекта, а целью работы оставался аудит, отладка и подготовка предложений.

Рабочее дерево уже содержало большое количество изменений, удалённых файлов и новых тестов до этого аудита. Поэтому отчёт описывает фактическое текущее состояние файлов и не восстанавливает прежние версии. В этом проходе изменены только этот отчёт и корневой SKILL.md; производственный код не переписывался.

## Тест, который сейчас падает

VKVideoDesktop.Tests.Integration.SqliteTests.PlaylistDatabase_AddVideoAsync_ConcurrentAdd_DoesNotLoseVideos ожидает 10 видео в плейлисте, но получает 1.

Причина находится в src/VKVideoDesktop.Data/Database/PlaylistDatabase.cs:122-135: метод сначала читает весь плейлист, добавляет видео в объекте и затем записывает весь JSON обратно. Параллельные вызовы читают одну и ту же старую версию и последний записавший вызов затирает результаты остальных.

Предлагаемое исправление:

1. Краткосрочно сериализовать операции изменения одного SQLite-файла через асинхронную блокировку и выполнять чтение и запись внутри одного критического участка.
2. Надёжнее вынести видео плейлиста в отдельную таблицу PlaylistVideos с уникальным ключом PlaylistId и VideoId, внешним ключом, порядком и атомарными INSERT/DELETE. Хранение изменяемого списка в одном JSON-поле плохо подходит для конкурентных операций.
3. Оставить этот тест как регрессионный и добавить параллельные проверки для RemoveVideoAsync и ReorderVideoAsync.

## Критические ошибки

### 1. Файл настроек удаляется при каждом обычном запуске

Файл: src/VKVideoDesktop.App/App.xaml.cs:230-244.

Код удаляет settings.json, если его содержимое содержит строку AccessToken. SettingsService.SaveAsync сериализует свойство AccessToken даже при пустом или null-значении, поэтому эта строка присутствует в обычном корректном JSON. При сохранённом токене она также присутствует всегда.

Последствия:

- настройки пользователя теряются при запуске;
- DPAPI-токен удаляется до вызова SettingsService.LoadAsync;
- ветка LoadAsync фактически обходится для стандартного файла настроек;
- пользователь получает сброс языка, темы, папки загрузок, прокси и других параметров.

Исправление: удалить ручное чтение и удаление файла из StartupAsync и всегда вызывать ISettingsService.LoadAsync. Повреждённый JSON и DPAPI-ошибка уже должны обрабатываться внутри SettingsService; при ошибке нужно создать значения по умолчанию и записать диагностическое событие с исключением. Добавить интеграционный тест запуска, который сохраняет настройки и проверяет, что следующий запуск их загружает и не удаляет файл.

### 2. Неполная загрузка может считаться успешной

Файл: src/VKVideoDesktop.Infrastructure/Download/DownloadEngine.cs:121-177.

При свободном месте менее 1 MiB цикл чтения выполняет break, после чего код сбрасывает поток, перемещает .part в конечный файл и возвращает IsSuccess = true. Аналогично нет финальной проверки, что реально записанный размер соответствует ожидаемому totalBytes.

Последствия:

- повреждённый или обрезанный файл может появиться как готовый;
- менеджер помечает загрузку завершённой;
- повторный запуск не всегда сможет отличить корректный результат от неполного.

Исправление:

- возвращать ErrorType.InsufficientSpace, если загрузка прервана из-за места;
- перемещать .part только после успешного чтения и проверки размера;
- сравнивать фактический размер с ожидаемым размером ответа и обрабатывать несовпадение как неполный HTTP-ответ;
- сохранять .part для возобновления, если это разрешено настройкой;
- сделать проверку свободного места через отдельную абстракцию, чтобы её можно было надёжно тестировать.

Добавленные сейчас интеграционные тесты загрузок используют TestDownloadEngine, а не production-класс DownloadEngine. Они не ловят этот дефект. Нужен локальный HTTP-сервер для реального DownloadEngine с ответом, который обрывается раньше Content-Length, и отдельным сценарием критически малого места.

### 3. Прогресс загрузки не сохраняется в SQLite

Файлы: src/VKVideoDesktop.Infrastructure/Download/DownloadManager.cs:234-251, src/VKVideoDesktop.Data/Database/DownloadDatabase.cs:161-170.

Менеджер обновляет свойства объекта в памяти, но не вызывает UpdateProgressAsync. Сам UpdateProgressAsync принимает параметр progress, однако записывает только DownloadedBytes; процент, скорость и прогресс отсутствуют в схеме сохранения.

Последствия:

- после перезапуска UI показывает устаревший или нулевой прогресс;
- восстановление .part может продолжиться технически, но состояние задачи и экран загрузок расходятся;
- параметр progress вводит в заблуждение и теряется.

Исправление: добавить в миграцию колонку Progress либо вычислять процент по DownloadedBytes и TotalBytes, вызывать сохранение прогресса с ограничением частоты, например раз в 250–500 мс или после каждого MiB, и покрыть это тестом восстановления.

## Ошибки загрузок и состояния UI

### 4. Удаление записи из UI не удаляет запись из хранилища

Файл: src/VKVideoDesktop.App/ViewModels/DownloadsViewModel.cs:72-86.

RemoveDownloadAsync удаляет только объект из ObservableCollection и завершает задачу. ClearCompletedAsync делает то же самое, причём LoadDownloadsAsync исключает завершённые задачи из коллекции, поэтому очистка завершённых загрузок обычно не находит ни одной записи.

Исправление:

- вызывать _downloadService.RemoveAsync(downloadId, deleteFile: false, cancellationToken);
- явно решить, удаляется ли конечный файл при удалении записи;
- для очистки завершённых получить записи из репозитория и удалить их через сервис;
- после операции обновлять коллекцию из репозитория;
- добавить тест именно для DownloadsViewModel, а не только тест вызова метода интерфейса через Moq.

### 5. Страница загрузок не загружает сохранённые задачи

Файл: src/VKVideoDesktop.App/Views/DownloadsPage.xaml.cs:11-21.

Конструктор получает ViewModel и задаёт DataContext, но не вызывает LoadDownloadsAsync. Метод существует в ViewModel, однако в текущем коде нет явного вызова при открытии страницы. После перезапуска записи из downloads.db могут не появляться на экране.

Исправление: загрузить данные в OnNavigatedTo с обработкой исключения, либо использовать отдельный асинхронный метод и жизненный цикл страницы. Не запускать необработанный fire-and-forget из конструктора.

### 6. События прогресса могут менять WinUI-коллекцию не из UI-потока

Файл: src/VKVideoDesktop.App/ViewModels/DownloadsViewModel.cs:98-105.

DownloadManager вызывает события из фоновой цепочки загрузки. DownloadsViewModel изменяет свойства элементов без гарантированного перехода через DispatcherQueue. В зависимости от контекста создания Progress<T> это может приводить к нестабильным обновлениям и ошибкам биндинга WinUI.

Исправление: передавать DispatcherQueue в слой UI и оборачивать изменения ObservableCollection и связанных свойств в TryEnqueue. Добавить UI-интеграционный тест или минимальный тест диспетчеризации.

### 7. CancellationTokenSource менеджера не очищаются

Файл: src/VKVideoDesktop.Infrastructure/Download/DownloadManager.cs:200-201, 320-323.

Источник отмены добавляется в _cancellations, но в finally не удаляется и не освобождается. При паузе, отмене и удалении источник удаляется вручную, однако обычное завершение, ошибка или исчерпание повторов оставляют запись.

Исправление: в finally удалять и освобождать именно тот CTS, который принадлежит текущему запуску, с защитой от гонки повторного запуска. Также реализовать IDisposable для SemaphoreSlim и оставлять одного владельца жизненного цикла каждой загрузки.

### 8. Восстановление загрузок игнорирует настройку пользователя

Файл: src/VKVideoDesktop.App/App.xaml.cs:268-273.

RecoverIncompleteDownloadsAsync вызывается без проверки UserSettings.AutoResumeAfterStartup. При выключенной настройке приложение всё равно переводит незавершённые задачи в очередь и запускает их.

Исправление: сначала загрузить настройки, затем вызывать восстановление только при включённом флаге. При выключенном флаге оставить задачи в состоянии Paused или отдельном состоянии Interrupted.

## Логирование и запуск приложения

### 9. Путь логов расходится с правилами проекта

Файлы: src/VKVideoDesktop.App/App.xaml.cs:122,154-168.

AGENTS.md задаёт %LOCALAPPDATA%\VKVideoDesktop\Logs\log-.txt, а код использует каталог log и шаблон app-.log. Фактически найден файл %LOCALAPPDATA%\VKVideoDesktop\log\app-20260911.log.

Исправление: выбрать единый путь из AGENTS.md, создать каталог до конфигурации Serilog и использовать единый шаблон имени. Не смешивать в одном приложении Serilog.Log и только scoped ILogger, если статический Log.Logger не настроен.

### 10. Статический Serilog используется до настройки и отдельно от DI

Файлы: src/VKVideoDesktop.App/App.xaml.cs:116-118,154-168, src/VKVideoDesktop.App/Program.cs:20-31.

Приложение пишет через Serilog.Log до построения host, а AddSerilog получает отдельный экземпляр, созданный в конфигурации DI. Это создаёт риск, что ранние сообщения и сообщения из Program.Main не попадут в файл.

Исправление: настроить Log.Logger в самом начале Main до первого сообщения, передать его в logging provider и вызвать Log.CloseAndFlush при завершении. Проверить тестом или запуском, что ранняя ошибка старта действительно появляется в журнале.

### 11. MainWindow зарегистрирован в DI, но создаётся вручную

Файлы: src/VKVideoDesktop.App/App.xaml.cs:193, src/VKVideoDesktop.App/Program.cs:48-83.

MainWindow зарегистрирован как singleton, но Program дважды выполняет new MainWindow(logger). В итоге объект из DI и реально показанное окно могут быть разными экземплярами, а зависимости и жизненный цикл singleton не гарантируются.

Исправление: получать окно через App.Services.GetRequiredService<MainWindow>. Если нужен аварийный минимальный режим, отделить его от обычного DI-сценария и не создавать две обычные копии окна.

### 12. Утечка COM-ссылки в системном трее

Файл: src/VKVideoDesktop.App/App.xaml.cs:456-458.

Marshal.GetIUnknownForObject(_mainWindow) возвращает указатель, который сохраняется в локальную переменную и не освобождается. Переменная handle также не используется.

Исправление: удалить этот код, если он не нужен, либо обернуть указатель в try/finally и вызвать Marshal.Release. Проверить, зачем он был добавлен, прежде чем сохранять его в рабочем коде.

## SQLite и миграции

### 13. Конкурентное применение миграций не защищено полностью

Файл: src/VKVideoDesktop.Data/Database/SchemaMigration.cs:19-31.

Проверка IsApplied выполняется до открытия транзакции. Два процесса могут одновременно увидеть отсутствие версии и оба попытаться выполнить одну миграцию. Текущие тесты проверяют идемпотентность, но не одновременную инициализацию нескольких экземпляров базы.

Исправление: сериализовать инициализацию базы, использовать транзакцию с подходящим режимом блокировки SQLite и уникальную запись версии с обработкой конфликта. Добавить тест, который создаёт несколько экземпляров каждой базы одновременно.

### 14. Nullable-поля читаются как обязательные

Файлы: src/VKVideoDesktop.Data/Database/DownloadDatabase.cs:194-196, src/VKVideoDesktop.Data/Database/HistoryDatabase.cs:67-68,93-94.

Схема допускает NULL в DownloadedBytes, Speed, RetryCount, Duration и LastPosition, но маппинг использует GetInt64, GetDouble и GetInt32 без IsDBNull. Новые объекты обычно записывают нули, поэтому текущие тесты проходят, но старая или вручную изменённая база может упасть при чтении.

Исправление: либо сделать колонки NOT NULL с миграцией значений по умолчанию, либо читать nullable безопасно и преобразовывать NULL в 0/TimeSpan.Zero. Тесты должны сначала вставлять настоящий SQL NULL напрямую, а не только передавать null в поля, которые сервис затем заменяет значением.

## VK API и отмена

### 15. Ошибки VK API теряют тип и отмена подавляется

Файл: src/VKVideoDesktop.Infrastructure/VkApi/VkVideoProvider.cs:60-72,89-98,116-137,163-174,194-204.

Все исключения перехватываются общим catch (Exception), после чего методы возвращают пустой список или null. OperationCanceledException также превращается в успешный с точки зрения вызывающего слоя пустой результат. В модели ответа есть VkError, но его поля не переводятся в доменное исключение или ErrorType.

Исправление:

- отдельно пробрасывать OperationCanceledException;
- различать 401, 403, 408, 429 и 5xx;
- переводить VK JSON-ошибки в типизированный результат;
- не скрывать от UI разницу между пустым результатом, авторизационной ошибкой и сетевым сбоем;
- добавить тесты с настоящим HttpMessageHandler для HTTP-статусов и JSON-ошибки VK.
